## Story
**As a** jogador que registra hunts,
**I want** excluir uma hunt registrada que não devia estar lá (duplicada, teste, erro de colar o texto errado),
**so that** meu histórico e meu profit (Meu Profit, Hunts Compartilhadas) fiquem corretos, sem precisar de ninguém além de mim pra corrigir isso.

## Acceptance Criteria
1. Given uma hunt registrada, When o usuário clica em "Excluir" no card e confirma, Then a hunt some da lista e é removida do banco (incluindo `session_monsters`/`session_items` relacionados, via cascade).
2. Given o usuário clica em "Excluir" mas cancela a confirmação, When a caixa de confirmação é fechada sem confirmar, Then nada é excluído e a hunt continua na lista.
3. Given a hunt excluída estava compartilhada (`is_shared = true`), When removida, Then também some da tela "Hunts Compartilhadas" (consequência natural do `delete`, sem lógica extra — a view pública já depende da linha existir em `sessions`).

## Complexity
T-shirt size: **XS** — 1 função nova num hook já existente, 1 botão num componente já existente. Sem migration (RLS já permite delete pelo dono), sem tabela nova, sem componente novo.

## Business Value
Fecha uma lacuna real: hoje não existe nenhuma forma de corrigir um erro de registro (hunt duplicada, teste, texto colado errado) sem mexer direto no banco. Pedido do usuário depois de testar o app.

## Decisões de Escopo (tomadas com o usuário antes do draft)
- **Sem usuário admin.** Cada dono exclui só as próprias hunts — mesmo modelo de permissão (RLS por `user_id`) já usado em todo o resto do app. Avaliado e descartado pelo usuário: um admin "com acesso a tudo" adicionaria um conceito de privilégio que não existe em nenhum outro lugar do sistema, sem necessidade real (app de uso pessoal).
- **Botão direto no card**, não dentro do modal de detalhe (`HuntDetailModal`). Confirmado com o usuário: "acho que apenas um botão excluir no card da hunt já é o suficiente".

## Risks
- **Exclusão acidental:** mitigado com `window.confirm` antes de excluir — mesmo padrão já usado em `Settings.jsx` (`handleRemoveCharacter`) pra remover personagem, sem introduzir um `Modal` novo pra uma ação já coberta por esse padrão mais simples.
- **Nenhum risco de dado órfão:** `session_monsters`/`session_items` já têm `on delete cascade` pra `sessions` (`supabase/schema.sql`), confirmado antes do draft — excluir a sessão já limpa tudo relacionado automaticamente.

## Dev Notes

**Padrão a seguir (fonte real, já existente):**
`useSessions.js` já tem `toggleShare` (linhas 73-79) fazendo exatamente o padrão que `removeSession` deve seguir: chamada direta ao Supabase, sem passar por `loadSessions()` de novo, atualizando o array local (`setSessions`) no sucesso. `removeSession` filtra em vez de mapear.
[Source: src/hooks/useSessions.js#L73-79]

**RLS já cobre isso — sem migration:**
`supabase/schema.sql#L65-68` já define a policy `Users manage own sessions` como `for all` (não só `select`), então `delete` já está liberado pro dono via `character_id in (select id from characters where user_id = auth.uid())`. Confirmar isso é só uma verificação de leitura do schema já existente, não uma mudança.
[Source: supabase/schema.sql#L60-68]

**Cascade já configurado:**
`session_monsters` e `session_items` (`supabase/schema.sql#L34-46`) têm `session_id uuid not null references sessions(id) on delete cascade` — excluir a sessão já remove essas linhas relacionadas automaticamente, sem query extra.
[Source: supabase/schema.sql#L34-46]

**Padrão de confirmação a seguir:**
`Settings.jsx` (`handleRemoveCharacter`) já usa `window.confirm(...)` antes de uma exclusão destrutiva — mesmo padrão, texto adaptado pro contexto de hunt.
[Source: src/pages/Settings.jsx]

**Fora de escopo:**
- Excluir múltiplas hunts de uma vez (seleção em lote) — não foi pedido.
- Qualquer botão de excluir dentro de `HuntDetailModal` ou na tela "Hunts Compartilhadas" (hunts de outros usuários nunca são exclúiveis por quem não é dono — RLS já bloqueia isso a nível de banco, e a UI de "Hunts Compartilhadas" não deve nem tentar mostrar essa opção).
- Usuário admin — decisão de escopo já fechada acima.
