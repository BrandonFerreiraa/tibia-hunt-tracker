## Story
**As a** sistema,
**I want** cachear localmente (Supabase) os dados de criaturas vindos da TibiaData API,
**so that** os cards e o modal de hunt (Stories 4.2/4.3) possam exibir imagem/HP/XP/loot de monstro sem depender de uma chamada externa a cada renderização, e sem quebrar quando a API estiver fora do ar.

## Acceptance Criteria
1. Given um `monster_name` que corresponde a uma criatura existente na TibiaData e ainda não cacheada, When `getCreature(monsterName)` é chamado, Then a criatura é buscada em `GET /v4/creature/{monster_name}`, salva (upsert) em `creatures` e retornada com `name`, `race`, `image_url`, `hitpoints`, `experience_points`, `is_lootable`, `loot_list`.
2. Given um `monster_name` já cacheado com `synced_at` recente (< 30 dias), When `getCreature(monsterName)` é chamado, Then nenhuma chamada à API externa é feita — o registro é lido direto do Supabase.
3. Given um `monster_name` que não corresponde a nenhuma criatura na TibiaData (API retorna 404) ou a API está indisponível (erro de rede/5xx), When `getCreature(monsterName)` é chamado, Then a função retorna `null` sem lançar exceção.
4. Given a tabela `creatures`, When lida por qualquer usuário autenticado, Then a policy de RLS permite `select`; `insert`/`update` só ocorrem via chamadas da própria aplicação (mesmo client autenticado, sem exigir role especial — dado é cache de API pública, não sensível).

## Complexity
T-shirt size: **S** — 1 tabela nova + 1 função de API + 1 helper de cache com upsert.

## Business Value
Base de dados para as Stories 4.2 (mini-ícones nos cards) e 4.3 (modal de detalhes com stats de monstro) — sem essa story, as duas ficariam sem fonte de dado real de criatura.

## Risks
- **Nome do monstro não bater com a API:** mitigado por normalização simples (lowercase) + tolerância já confirmada da própria API (`"crypt warrior"` resolve corretamente) + fallback `null` no helper, nunca lança erro.
- **Cache desatualizado:** dados de criatura (HP, XP, loot) mudam raramente em Tibia; TTL de 30 dias é suficiente e evita re-fetch excessivo.

## Dev Notes

**Contexto:**
- `src/lib/tibiaDataClient.js` já tem o padrão de tratamento de erro (`TibiaDataUnavailableError`, `CharacterNotFoundError`) usado por `fetchCharacter`/`fetchHighscorePage` — `fetchCreature` reaproveita a mesma estrutura de fetch, mas devolve `null` em 404 em vez de lançar, porque aqui "não encontrado" é um caminho normal (nome de monstro que não bate com a API), não um erro pro usuário ver.
- Confirmado manualmente que a API tolera nomes com espaço/case (`GET /v4/creature/crypt%20warrior` → resolve para `race: "cryptwarrior"`, `name: "Crypt Warriors"` corretamente) — não é necessário um dicionário de slugs.
- `session_monsters.monster_name` (schema em `supabase/schema.sql`) é texto livre do parser do Session Analyser — é essa string (normalizada) que vira a chave de busca.
- Tabela `creatures` é cache global (não por usuário) — um monstro buscado por qualquer usuário fica disponível para todos, reduzindo chamadas à API externa.

**Fora de escopo:**
- Sync periódico/agendado (cron) — cache é lazy, populado sob demanda pela própria aplicação.
- Qualquer UI — esta story é só a camada de dados (`Stories 4.2/4.3` consomem `getCreature`).

### Testing
- Testar `getCreature('Demon')` → deve retornar HP 8200, XP 6000, loot_list com itens.
- Testar `getCreature('monstro que não existe')` → deve retornar `null`, sem lançar.
- Testar chamada repetida para o mesmo monstro → segunda chamada não deve gerar request de rede (verificar via `read_network_requests` ou log).
