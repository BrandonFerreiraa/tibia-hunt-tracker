## Story
**As a** jogador de Tibia que farma pra viver,
**I want** definir uma meta de profit em KK com data inicial e final, e ver quanto preciso fazer por dia recalculado automaticamente (inclusive quando um dia fico devendo),
**so that** eu saiba exatamente o quanto preciso hunt-ar hoje pra continuar no caminho de bater minha meta, sem precisar recalcular na mão toda vez que um dia sai diferente do planejado.

## Acceptance Criteria
1. Given uma meta ativa de 10kk de 01/09 a 10/09 (10 dias), When nenhum profit foi feito ainda, Then a meta diária exibida é 1kk/dia.
2. Given a mesma meta, When um dia passa sem nenhum profit registrado, Then no dia seguinte a meta diária recalculada aumenta corretamente para cobrir o déficit dividido pelos dias restantes (ex.: 0 feito no dia 1 → dia 2 em diante mostra 9kk / 9 dias = ainda 1kk/dia; se também nada for feito no dia 2, dia 3 mostra 9kk / 8 dias = 1,125kk/dia).
3. Given a meta é batida antes do `end_date`, When o painel é exibido, Then mostra claramente que a meta já foi atingida (sem pedir mais profit por dia).
4. Given o `end_date` passa sem o alvo ser atingido, When o usuário acessa a página, Then a meta aparece no histórico como não batida, com o resultado final.
5. Given metas passadas no histórico, When exibidas, Then mostram valor alvo, período, resultado e profit final acumulado.
6. Given uma meta ativa em andamento, When o usuário tenta criar uma nova meta, Then vê uma confirmação explícita de que isso vai encerrar a meta atual antes de prosseguir.

## Complexity
T-shirt size: **L** — lógica de recálculo com casos-limite (último dia, meta batida antes do fim, fechamento automático ao expirar), depende das Stories 6.1 (schema) e 6.2 (conversor, pra mostrar a meta diária também em TC/Reais).

## Business Value
É o núcleo do pedido original do usuário: saber exatamente quanto precisa "farmar" por dia pra bater a meta, com a meta se ajustando sozinha quando a vida real atrapalha o plano — sem isso, o conversor de moeda (Story 6.2) sozinho não resolve o problema real.

## Risks
- **Fórmula quebra no caso-limite do último dia (`dias_restantes = 0`) ou quando a meta já foi batida:** mitigado tratando esses 2 casos explicitamente antes da divisão (ver `computeDailyTarget` nas Dev Notes) — nunca dividir por zero, nunca mostrar meta diária negativa.
- **Fechamento automático de meta expirada perder profit registrado depois do `end_date` mas antes do usuário abrir o app:** mitigado calculando o profit acumulado **só dentro do intervalo `[start_date, end_date]`** da meta (sessões com `started_at` fora desse intervalo não contam), então não importa quando o usuário abre o app — o resultado é sempre o mesmo.
- **Criar meta nova sem querer perde visibilidade do progresso da meta ativa:** mitigado com confirmação explícita na UI (AC 6) antes de encerrar.

    // today, startDate, endDate como dayKey strings (YYYY-MM-DD)
    const remaining = targetGold - profitSoFarGold
    if (remaining <= 0) return { met: true, dailyTargetGold: 0 }
    const effectiveToday = today < startDate ? startDate : today
    const daysRemaining = daysBetweenInclusive(effectiveToday, endDate) // >= 1 se today <= endDate

## Dev Notes

**Fórmula de redistribuição (a mesma dada pelo usuário no requirements gathering, verificada no exemplo do AC 2):**
`meta_diária = (valor_alvo − profit_já_feito_no_período) / dias_restantes_no_período` (incluindo hoje). Não existe um valor por dia armazenado no banco — é sempre derivado ao vivo do profit real, o que já é a "redistribuição automática" pedida: se um dia fica devendo, o dia seguinte automaticamente mostra um valor maior.

**Fonte do profit — reaproveitar, não duplicar lógica:**
`src/hooks/useProfitStats.js` já busca `sessions` com `balance` de **todos os personagens do usuário** (sem filtro de `character_id`), confiando só em RLS — exatamente o escopo "por conta" confirmado com o usuário (não por personagem individual). `src/lib/groupSessionsByDay.js` já tem `dayKey()` pronto pra normalizar `started_at` em string `YYYY-MM-DD` — reaproveitar essa função em `profitInRange`, não reimplementar comparação de datas.
[Source: src/hooks/useProfitStats.js#L1-L31; src/lib/groupSessionsByDay.js#L1-L7]

**Schema desta story (da Story 6.1, já deve estar aplicado):**

[Source: docs/stories/6.1.schema-taxas-cambio-metas.md]

**Finding 1 (não bloqueante, recomendo registrar como débito técnico) — inconsistência de estado se o `update` de fechamento falhar:**
Em `closeGoalInDb` (`src/hooks/useGoals.js:6-16`), se o `supabase...update(...)` falhar (`error` truthy), a função retorna um objeto local `{ ...goal, status, final_profit_gold: profitGold }` **como se o fechamento tivesse funcionado**, sem indicar o erro pra quem chamou. Isso acontece em 2 lugares: (a) `closeExpiredIfNeeded` dentro de `load()` — a meta expirada some do `activeGoal` e aparece no histórico local mesmo que o `update` real no banco tenha falhado (a linha continua `active` no Postgres); (b) `createGoal` — a meta anterior é tratada como fechada localmente, e a nova meta é inserida como `active`, mas o índice único parcial (`one_active_goal_per_user`, Story 6.1) vai **rejeitar essa inserção** no banco (já existe uma linha `active` pro mesmo usuário), fazendo o `insert` falhar — erro que o `GoalForm` não verifica (Finding 2). Resultado: nessa sessão o usuário vê uma tela inconsistente (meta "fechada" no histórico, mas nenhuma meta nova ativa), embora um reload da página corrija sozinho (o próximo `load()` busca o estado real do banco, que ainda tem a meta antiga como `active`) — não há perda de dados, só uma janela de estado incorreto na sessão atual. Sugestão de fix: em caso de erro no `update`, não tratar como fechado — manter a meta anterior visível como ativa e surfacear o erro.

**Finding 2 (não bloqueante, mesmo padrão do finding da Story 6.2):** `GoalForm.submit` chama `await onCreate(...)` e ignora o `{ error }` retornado — se a criação falhar (pelo cenário do Finding 1, ou por qualquer outro erro de rede/RLS), o formulário só reseta os campos como se tivesse dado certo, sem nenhuma mensagem. Mesma recomendação da 6.2: adotar o padrão de `error` local + `<p className="text-sm text-danger">` já usado em `CharacterForm.jsx`/`AccountSettings.jsx`.

**Limitação desta revisão (herdada do Dev):** sem credenciais de login do usuário, não testei o fluxo autenticado ao vivo (criar meta real, ver o painel recalculando, ver uma meta expirar de verdade).
