## Story
**As a** jogador com personagem verificado,
**I want** ver level, vocação, guild e minha posição no highscore da skill principal,
**so that** eu tenha um perfil confiável pra comparar com outras hunts, sem depender de dados que eu mesmo digitei.

## Acceptance Criteria
1. Given personagem verificado, When a página de perfil é aberta, Then mostra level/vocação/guild/achievement points, com timestamp "atualizado há X".
2. Given o personagem aparece no highscore da sua skill principal (lista completa de até 1000 posições, não uma amostra), When o sync de skill roda, Then exibe o valor exato da skill junto com o rank.
3. Given o personagem NÃO aparece no highscore daquela categoria, When o sync roda, Then nenhum dado de skill é exibido — sem erro, sem "0".
4. Given a TibiaData API está indisponível, When o sync falha, Then a página mostra o último dado em cache (se houver) sem quebrar.
5. Given o personagem é Knight, When o usuário escolhe qual skill acompanhar (Club/Axe/Sword/Shielding Fighting), Then o sync busca só aquela categoria — não varre as 4 automaticamente (custo/tempo).
6. Given os dados de stats/skill alimentam o feed público (Story 2.3), When um usuário tenta escrever esses campos direto via client, Then a escrita é bloqueada (mesma lógica de segurança da Story 2.1 — só a função privilegiada pode gravar).

## Complexity
T-shirt size: **L** — duas funções privilegiadas no banco (profile sync rápido + skill sync com scan paginado), UI de seleção de categoria pra Knights, cache com cooldown.

## Business Value
Sem dados reais confiáveis, o feed de hunts (Story 2.3) mostraria "level/vocação" que qualquer um poderia ter inventado — isso mata a credibilidade do produto.

## Risks
- **Spoofing de stats** (mesma classe de risco da Story 2.1) — mitigado por AC 6: sync roda em função `SECURITY DEFINER`, cliente sem GRANT de UPDATE nas colunas de stats.
- **Custo de scan paginado** (até 20 requisições sequenciais por skill) — mitigado por: só roda sob ação explícita do usuário (botão "Sincronizar"), com cooldown mínimo entre syncs (evita spam contra a API gratuita da comunidade).
- **TibiaData API instável** (já vimos isso ao vivo na Story 2.1) — mitigado por cache + degradação graciosa (AC 4).

## Dev Notes

**Contexto (Story 2.1, TibiaData API):**
- Padrão de segurança estabelecido na Story 2.1: `SECURITY DEFINER` + `revoke update (...) from authenticated` + `grant update (colunas permitidas) to authenticated`. Reutilizar o mesmo padrão aqui.
- `http` extension já habilitada (`create extension if not exists http;`, idempotente).
- **Confirmado ao vivo:** highscores retornam no máximo 1000 registros por categoria/mundo (`total_pages: 20`, `total_records: 1000`) — é a lista completa, não uma amostra. Isso vale pra qualquer combinação de mundo/categoria testada.
- **Confirmado ao vivo:** para achar um personagem específico numa categoria, a vocação no parâmetro da URL deve ser `all` — alguns mundos estão em "restriction mode" e só aceitam `all` (erro 9002 se tentar filtrar por vocação específica nesses mundos). Usar sempre `all` evita esse problema em qualquer mundo.
- Mapeamento de categoria por vocação (Knight tem 4 opções, as outras têm 1 automática):
  ```
  Knight/Elite Knight → escolha do usuário entre: clubfighting, axefighting, swordfighting, shielding
  Paladin/Royal Paladin → distancefighting
  Druid/Elder Druid → magiclevel
  Sorcerer/Master Sorcerer → magiclevel
  ```
- `src/lib/tibiaDataClient.js` (Story 2.1) já tem `fetchCharacter()` e `fetchHighscorePage()` client-side — **não serão usados para o sync real** (que agora é 100% server-side, mesma lógica de segurança). Podem ficar no arquivo como referência/uso futuro (ex: preview antes de sincronizar) ou ser removidos se não usados — decisão do @dev na implementação.

### Testing
- Testes automatizados (mesmo padrão dos scripts `dev-test-*` da Story 2.1): tentar escrever `stats_level` direto via client (deve falhar), rodar `sync_character_profile` contra um personagem real, rodar `sync_character_skill` com uma categoria válida.
- Teste de cooldown: chamar a RPC duas vezes em sequência rápida, confirmar que a segunda é rejeitada.
- Teste de "não encontrado no highscore": usar um personagem de nível baixo (não deve estar no top 1000) e confirmar que os campos de skill ficam null sem erro.

### Debug Log References
- **Bug real encontrado e corrigido:** `http_get()` pode lançar exceção dura (timeout, "HTTP request cancelled") em vez de retornar uma resposta com status ruim. A primeira versão só tratava `response.status`, deixando essas exceções estourarem como erro cru do Postgres. Corrigido com `BEGIN/EXCEPTION` em volta de cada chamada (`migrations/008`).
- **Bug real encontrado e corrigido:** 20 chamadas HTTP sequenciais (~1.4-3.3s cada, observado ao vivo) somam bem mais que o `statement_timeout` padrão do Supabase para a role `authenticated`, matando a função no meio do loop de forma não capturável pelo `EXCEPTION` (é um cancelamento externo, não uma exceção lançada dentro do bloco). Corrigido com `set statement_timeout` específico nas duas funções (`migrations/009`), depois ajustado de 45s/4s para 90s/8s por requisição ao observar latência real maior que o esperado (`migrations/010`).
- **Ajuste de UX:** a versão inicial limpava `stats_skill_category` junto com valor/rank quando não encontrado, perdendo a informação de qual categoria foi checada. Corrigido pra manter a categoria e só zerar valor/rank (`migrations/011`).
- **Confirmado ao vivo:** o limite de 1000 registros por categoria/mundo é real (não uma amostra arbitrária) — `highscore_page.total_pages: 20` em toda combinação testada.
- **Confirmado ao vivo:** alguns mundos exigem `vocation=all` na URL do highscores ("restriction mode", erro 9002 se filtrar por vocação específica) — usar sempre `all` e filtrar pelo nome evita esse problema universalmente.
