## Story
**As a** jogador navegando pelo feed de hunts compartilhadas,
**I want** que a aba se chame "Hunts Compartilhadas" e que minhas próprias hunts tenham um destaque visual na lista,
**so that** eu identifique de relance o que é meu e o que é de outros jogadores, sem precisar de uma aba/filtro separado.

## Acceptance Criteria
1. Given a navegação do app, When usuário olha as abas, Then o que hoje se chama "Feed" aparece como "Hunts Compartilhadas".
2. Given uma hunt compartilhada de um personagem cadastrado pelo usuário logado, When a lista carrega, Then o card dessa hunt exibe um badge "Sua hunt".
3. Given uma hunt compartilhada de um personagem que não é do usuário logado, When a lista carrega, Then o card não exibe o badge.
4. Given os filtros/ordenação já existentes (monstro, mundo, vocação, data, sort), When aplicados, Then continuam funcionando normalmente, com o badge presente nos cards certos.
5. Given a view pública `public_hunts_feed`, When consultada por qualquer usuário autenticado, Then continua **sem expor `user_id` de ninguém** — a identificação de "sua hunt" usa `character_id` (já público/visível via `character_name` no card), nunca o id da conta.

## Complexity
T-shirt size: **S** — 1 coluna nova na view (append-only) + comparação client-side + troca de texto na nav.

## Business Value
Segunda metade do pedido original do usuário sobre a tela de hunts compartilhadas (a primeira metade — feed único com todos os usuários — já existe desde a Story 2.3).

## Risks
- **Vazar identidade de outro usuário:** a Story 2.3 deliberadamente **não expõe `user_id`** na view (comentário explícito na migration 012: "nunca user_id, verification_code"). Esta story mantém essa decisão — expõe só `character_id`, que já é implicitamente público via `character_name`/`world` exibidos no card. Nenhuma informação nova sensível é exposta.
- **Quebrar a view ao adicionar coluna:** a Story 2.4 já bateu nesse problema (`create or replace view` do Postgres não permite inserir coluna no meio da lista — só no final, erro `42P16`). `character_id` deve ser adicionado **no final** do `select` da view, não no meio.

## Dev Notes

**Contexto:**
- `public_hunts_feed` (migrations 012 e 013) hoje seleciona `s.id, s.hunt_name, s.started_at, s.duration_seconds, s.xp_per_hour, s.balance, c.name as character_name, c.world, c.verified, c.stats_level, c.stats_vocation, top_monsters, all_monster_names, profit_per_hour` — **sem `user_id`, por decisão deliberada de segurança/privacidade da Story 2.3**.
- `useHuntsFeed.js` faz `select('*')` na view — a coluna nova (`character_id`) chega automaticamente no client sem precisar tocar nesse hook.
- `useCharacters()` (Story 1.x, ajustado na 3.1) já retorna a lista de personagens do usuário logado com `id` — é só isso que esta story precisa dele em `HuntsFeed.jsx`, não o CRUD completo.
- `HuntsFeed.jsx` já tem um padrão de badge condicional pro selo de verificado (`{hunt.verified && <Badge variant="success">...}`) — seguir o mesmo padrão pro badge "Sua hunt".
- **Gotcha real de migration** (aconteceu na Story 2.4): Postgres recusa `create or replace view` se a coluna nova não estiver no final da lista (`42P16: cannot change name of view column`). `character_id` vai no final.

**Fora de escopo:**
- Aba/filtro separado só pra hunts próprias — usuário já decidiu que quer destaque visual na lista única, não uma aba nova (decisão tomada na fase de planejamento do Epic 3).
- Tela "Meu Profit" → Story 3.5.

### Testing

### Completion Notes List
- Desvio deliberado da task original: usei `variant="gold"` no badge "Sua hunt" em vez de `variant="success"` (sugerido na task) — o badge de verificado já usa `success` (verde) com outro significado; usar a mesma cor pros dois deixaria a UI confusa (dois badges verdes com sentidos diferentes lado a lado). `gold` já é usado pro badge "Maker" em `CharacterList.jsx`, mantendo o app com um vocabulário de cor consistente pra "atributo do usuário/dono".
- `ownCharacterIds` é recalculado a cada render (`new Set(...)`) — sem `useMemo`, porque a lista de personagens do usuário é pequena (poucas dezenas no máximo) e o custo é desprezível; evitei complexidade desnecessária.
- Migration `015` ainda **não aplicada em produção** — segue o mesmo padrão das anteriores (usuário aplica manualmente no SQL Editor).
- Não pude testar visualmente com hunts reais de mais de um usuário (sem credenciais/segunda conta) — recomendo conferir depois de aplicar a migration.
