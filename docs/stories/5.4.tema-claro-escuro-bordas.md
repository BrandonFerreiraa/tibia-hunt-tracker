## Story
**As a** usuário do TibiaHunt,
**I want** poder escolher entre tema claro e escuro, e ver a borda dos cards claramente em qualquer um dos dois,
**so that** eu use o app no visual que prefiro, sem perder a separação visual entre os elementos da tela.

## Acceptance Criteria
1. Given a tela de Configurações, When o usuário troca o tema (claro ↔ escuro), Then o app inteiro muda de aparência imediatamente, sem precisar recarregar a página.
2. Given um tema escolhido, When o usuário fecha e reabre o app (nova sessão de navegador), Then o mesmo tema continua ativo (persistido em `localStorage`).
3. Given um usuário que nunca escolheu um tema, When acessa o app pela primeira vez, Then o tema padrão é o escuro atual — ninguém tem a aparência trocada sem uma ação explícita.
4. Given qualquer card do app (personagens, hunts, profit, etc.), When exibido em qualquer um dos 2 temas, Then a borda tem contraste de pelo menos 3:1 contra o fundo do card (WCAG 1.4.11, non-text contrast) — **verificado por script, não estimado visualmente**.
5. Given o tema claro, When qualquer texto principal, secundário ou sutil é exibido sobre o fundo/superfície do tema, Then o contraste atende WCAG AA (>= 4.5:1 texto normal, >= 3:1 texto grande) — **verificado por script** pra cada par texto/fundo definido na nova paleta.

## Complexity
T-shirt size: **M** — paleta de cores nova + mecanismo de alternância + persistência, mas sem lógica de negócio nova, só CSS + 1 hook pequeno.

## Business Value
Fecha o Epic 5 e resolve os 2 últimos pontos de qualidade visual pedidos pelo usuário: bordas pouco visíveis e falta de tema claro.

## Risks
- **Paleta clara mal calibrada gerar contraste ruim:** mitigado pela AC 5 — validação por script, não por "parece que está bom".
- **Trocar tema quebrar alguma tela que usa cor fixa (não token):** levantamento rápido necessário durante o dev — todo o app hoje usa as classes Tailwind geradas a partir de `--color-*` (`text-gold`, `bg-surface`, etc.), então redefinir os tokens sob um seletor de tema deve refletir em tudo automaticamente, sem precisar tocar em cada componente.
- **Usuário achar o tema padrão diferente do que já usa:** mitigado pela AC 3 — default continua escuro, sem mudança de comportamento pra quem não mexer em nada.

## Dev Notes

**Contexto:**
- `index.css` usa Tailwind v4 (`@import 'tailwindcss'` + bloco `@theme`) — as classes utilitárias geradas (`text-gold`, `bg-surface`, `border-border`, etc.) referenciam `var(--color-X)` no CSS compilado, **não o valor hexadecimal fixo**. Isso significa que redefinir `--color-X` sob um seletor `[data-theme='light']` funciona em tempo real pra qualquer componente que já usa essas classes, sem precisar tocar em nenhum componente individualmente — é a mesma técnica de tema já usada em outros contextos (ex.: Artifacts da Anthropic usam o mesmo padrão `[data-theme]`).
- Todo o app hoje já usa exclusivamente as classes geradas pelos tokens (`text-text`, `text-text-muted`, `bg-bg`, `bg-surface`, `border-border`, `text-gold`, `text-danger`, `text-accent`, etc.) — não há cor hardcoded fora de `index.css` (confirmado ao longo das Stories 3.x-5.x, nenhuma delas introduziu cor fixa).
- `Card.jsx` (`src/components/ui/Card.jsx`) já usa `border border-border` — a Task 1 corrige o **valor** do token, não o componente.
- Skill `dataviz` (usada na Story 5.3) expõe `contrast(hexA, hexB)` em `scripts/validate_palette.js` — reaproveitar a mesma função pra validar os pares desta story, em vez de reescrever a fórmula de contraste do zero.

**Fora de escopo:**
- Detectar `prefers-color-scheme` do sistema operacional pra escolher o tema inicial — o default é sempre escuro (AC 3), sem detecção automática. Se o usuário quiser isso depois, é uma story separada.
- Qualquer ajuste de tema em `Login.jsx`/`Onboarding.jsx` além do que os tokens já cobrem automaticamente — essas telas usam os mesmos tokens (`bg-bg`, `text-text`, etc.), então já herdam o tema sem trabalho extra.

### Testing

**Bug encontrado (bloqueante):** `useTheme()` só é invocado dentro do componente `Settings.jsx` — o `useEffect` que aplica `document.documentElement.setAttribute('data-theme', theme)` só roda enquanto esse componente está montado. Como `App.jsx` renderiza só uma aba por vez (`view === 'settings' && <Settings />`), se o usuário recarregar a página estando em qualquer outra aba (ou ainda não logado, nas telas de Login/Onboarding), `Settings.jsx` nunca monta nessa sessão, e o tema salvo em `localStorage` nunca é aplicado — o app volta a mostrar o tema escuro (por ausência do atributo `data-theme`) mesmo com `'light'` salvo.

**Reprodução:**
```js
localStorage.setItem('theme', 'light')
location.reload()
// depois do reload, sem nunca ter ido em Configurações:
document.documentElement.getAttribute('data-theme') // null (esperado: 'light')
getComputedStyle(document.body).backgroundColor // rgb(10, 10, 15) — ainda escuro
```

**Causa raiz:** a leitura/aplicação do tema persistido precisa acontecer uma vez, no nível raiz do app (`App.jsx`, ou mais cedo ainda), independente de qual aba está ativa ou se o usuário já passou pelo login — não pode depender de `Settings.jsx` estar montado.

**Sugestão de fix:** mover a leitura inicial + aplicação do `data-theme` pra fora de `Settings.jsx` — por exemplo, chamar `useTheme()` uma vez em `App.jsx` (que já roda em toda sessão autenticada) e passar `theme`/`setTheme` como props pra `Settings.jsx`, ou extrair só a lógica de "aplicar o tema salvo" pra um efeito que rode fora do fluxo condicional das abas. Se quiser cobrir também as telas de Login/Onboarding (antes do login), a aplicação inicial precisaria rodar ainda mais cedo (ex.: em `main.jsx`, antes do primeiro render do React) — vale considerar dado que a tela de Login já usa os mesmos tokens de cor.
