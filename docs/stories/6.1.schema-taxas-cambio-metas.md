## Story
**As a** dono do app,
**I want** tabelas novas para guardar as taxas de câmbio (KK por TC, Reais por 250 TC) e as metas de profit de cada usuário, com RLS igual ao resto do sistema,
**so that** as próximas stories (conversor de moeda e painel de meta) tenham onde persistir esses dados com segurança, sem depender de nenhuma tabela existente ser alterada.

## Acceptance Criteria
1. Given um usuário sem taxas configuradas, When consulta `exchange_rates`, Then não há erro — ausência de linha é um estado válido (taxas ainda não configuradas).
2. Given um usuário salva as 2 taxas, When consulta de novo, Then só ele (via RLS) consegue ler/escrever sua própria linha.
3. Given um usuário com uma meta `active`, When tenta criar outra meta `active`, Then a meta anterior é automaticamente encerrada (`completed` ou `failed`, conforme progresso) antes da nova ser criada — nunca duas `active` simultâneas para o mesmo usuário.
4. Given uma meta com `end_date` no passado ainda marcada como `active`, When o app processa o fechamento (ver Story 6.3), Then seu `status` passa a refletir o resultado (`completed` se o profit acumulado no período >= `target_gold`, senão `failed`).

## Complexity
T-shirt size: **S** — 1 migration nova (2 tabelas + RLS + 1 índice único parcial), sem RPC nova, sem alteração em tabelas existentes.

## Business Value
Base de dados necessária para o conversor de moeda e o painel de meta (Stories 6.2 e 6.3) — sem isso nenhuma das duas funciona.

## Risks
- **Duas metas `active` simultâneas por corrida de condição (2 abas abertas, cliques rápidos):** mitigado por índice único parcial no banco (`status = 'active'`), que rejeita a segunda inserção em nível de banco mesmo se a aplicação falhar em fechar a anterior primeiro.
- **Tipo de coluna monetária inconsistente com `sessions.balance` (`bigint`, gold puro):** mitigado usando `bigint` também em `target_gold`, guardando sempre em gold puro (não em "kk") — a conversão pra "kk" é só de exibição (`src/lib/kkFormat.js`, criado na Story 6.2), igual ao padrão já usado em `Profit.jsx`.

## Tasks / Subtasks

- [x] Task 1 — Nova migration `supabase/migrations/023_currency_goals.sql` (AC: 1, 2)
  - [x] Tabela `exchange_rates`:
    ```sql
    create table if not exists exchange_rates (
      user_id uuid primary key references auth.users(id) on delete cascade,
      kk_per_tc numeric not null check (kk_per_tc > 0),
      brl_per_250tc numeric not null check (brl_per_250tc > 0),
      updated_at timestamptz not null default now()
    );
    alter table exchange_rates enable row level security;
    create policy "Users manage own exchange_rates"
      on exchange_rates for all
      using (user_id = auth.uid())
      with check (user_id = auth.uid());
    ```
    `user_id` como chave primária (não `id` próprio) porque é sempre 1 linha por usuário — upsert por `user_id`, sem necessidade de múltiplas linhas.
  - [x] Tabela `goals`:
    ```sql
    create table if not exists goals (
      id uuid primary key default gen_random_uuid(),
      user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
      target_gold bigint not null check (target_gold > 0),
      start_date date not null,
      end_date date not null check (end_date >= start_date),
      status text not null default 'active' check (status in ('active', 'completed', 'failed')),
      final_profit_gold bigint,
      created_at timestamptz not null default now(),
      ended_at timestamptz
    );
    create unique index if not exists one_active_goal_per_user
      on goals(user_id) where (status = 'active');
    alter table goals enable row level security;
    create policy "Users manage own goals"
      on goals for all
      using (user_id = auth.uid())
      with check (user_id = auth.uid());
    ```
    - `target_gold` em gold puro (bigint), igual a `sessions.balance` — mantém consistência de unidade em todo o schema; a conversão pra "kk" na UI acontece só na exibição/input (Story 6.2 cria `src/lib/kkFormat.js`).
    - `final_profit_gold` (nullable): preenchido só quando a meta é encerrada (`completed`/`failed`), guarda o profit acumulado no período no momento do fechamento — usado pelo histórico (Story 6.3) sem precisar recalcular a partir de `sessions` toda vez.
    - `one_active_goal_per_user`: índice único parcial garante em nível de banco que nunca existem 2 linhas `active` pro mesmo `user_id` (AC 3), mesmo se a aplicação falhar em fechar a anterior antes de inserir a nova.

## Dev Notes

**Padrão de RLS a seguir (fonte real, não inventado):**
`supabase/schema.sql` linhas 4-10 (`characters`) e 60-63 (policy) já usam exatamente o padrão `user_id uuid not null default auth.uid() references auth.users(id) on delete cascade` + `create policy ... using (user_id = auth.uid()) with check (user_id = auth.uid())`. As 2 tabelas novas desta story replicam esse padrão diretamente (sem passar por `characters`, já que a meta é "por conta", não por personagem — decisão confirmada na Story 12.5 do Epic 6 / requirements gathering do `@pm`).
[Source: supabase/schema.sql#L4-L10, L60-L63]

**Convenção de unidade monetária:**
`sessions.balance` é `bigint` em gold puro — não existe hoje nenhuma coluna em "kk" (milhões) em nenhuma tabela do projeto, e nenhuma formatação de "kk" no código (`src/pages/Profit.jsx` usa `toLocaleString('pt-BR')` direto sobre o valor em gold). `target_gold` segue esse mesmo padrão por consistência — a Story 6.2 é responsável por criar o helper de conversão kk↔gold pra exibição/input.
[Source: supabase/schema.sql#L23-L25 (sessions.loot/supplies/balance); src/pages/Profit.jsx#L8-L9 (formatNumber)]

**Numeração da migration:**
A última migration existente é `022_fix_creature_url_space_encoding.sql` — esta story cria `023_currency_goals.sql`, seguindo a sequência.
[Source: supabase/migrations/ (listagem: 002 a 022)]

**Fora de escopo desta story:**
- Nenhuma lógica de aplicação (hooks, UI) — só schema + RLS. Hooks `useExchangeRates` e `useGoals` são das Stories 6.2 e 6.3.
- Nenhuma RPC nova — toda a lógica de "fechar meta anterior ao criar uma nova" e "calcular status ao expirar" é feita em código de aplicação (hook), não em função de banco, seguindo o mesmo espírito de simplicidade das tabelas `characters`/`sessions` (que não têm triggers).

### Testing
