## Story
**As a** jogador de Tibia usando o conversor e a meta de profit,
**I want** digitar todo valor monetário (taxa de câmbio, meta, valor a converter) sempre em gold puro — a mesma unidade que já uso pra tudo mais no jogo — com o campo se formatando sozinho enquanto digito,
**so that** eu não precise fazer conversão mental nenhuma entre telas (hoje preciso digitar o mesmo profit em escalas diferentes no Conversor e na Meta), e consiga ler valores grandes sem contar zero por zero.

## Acceptance Criteria
1. Given a taxa configurada como 45.000 (gold por TC) e um profit de 80.000.000 (80kk) de gold, When convertido, Then o resultado bate com a conta manual (`80.000.000 / 45.000 ≈ 1.777,78 TC`) — mesma ordem de grandeza nos dois lados, sem precisar digitar valores em unidades diferentes.
2. Given qualquer um dos 4 campos monetários, When o usuário digita números, Then o campo mostra o valor formatado (separador de milhar, ou `R$` com centavos no caso da taxa em reais) em tempo real, sem exigir recarregar ou sair do campo.
3. Given uma meta criada antes desta correção (valores salvos como se fossem KK×1.000.000), When exibida depois da correção, Then **não é recalculada silenciosamente** — como não há dado de produção pra migrar até agora (nenhuma meta real foi criada em produção antes desta correção), não há bloqueio; se isso mudar antes da implementação, escalar antes de prosseguir.

## Complexity
T-shirt size: **L** — corrige a semântica de uma taxa já em produção (Story 6.2), remove um arquivo inteiro (`kkFormat.js`), cria 1 componente novo de input formatado, e toca em quase todos os subcomponentes de `Goals.jsx` (5 de 6). Não muda nenhuma tabela nova nem a lógica de `goalCalculator.js` (que já trabalha só em gold).

## Business Value
Corrige um erro real que o usuário encontrou ao tentar usar o Conversor e a Meta juntos: hoje é preciso lembrar de multiplicar/dividir por 1.000.000 dependendo de qual tela está aberta. Sem essa correção, o Epic 6 inteiro fica com uma armadilha de uso.

## Risks
- **Confusão entre "taxa antiga (KK)" e "taxa nova (Gold)" se alguém já tiver salvo uma taxa antes desta correção:** mitigado pelo AC 3 — como o epic confirmou que não há meta real de produção ainda, e a taxa de câmbio é só um número reconfigurável a qualquer momento (sem histórico), o usuário simplesmente reconfigura a taxa com o valor certo depois desta story. Nenhuma migração de dado necessária.
- **Cursor pular pro final do campo ao editar no meio de um valor já digitado** (efeito colateral comum de inputs com formatação ao vivo): aceito como trade-off consciente nesta story — ver Dev Notes pra a técnica recomendada (dígitos-como-string, sem tentar preservar posição do cursor). Não é bloqueante pra um campo de poucos dígitos como estes.
- **Story 6.4 (cancelar meta) mexe nos mesmos arquivos** (`Goals.jsx`, `useGoals.js` não — só `Goals.jsx`/`GoalHistory`): se as duas forem implementadas em paralelo, uma delas vai precisar re-aplicar sobre o resultado da outra. Mitigação: não há dependência lógica entre elas (podem ser feitas em qualquer ordem), só cuidado de merge se forem feitas ao mesmo tempo.

## Dev Notes

**Contexto do bug (não é feature nova, é correção):** a Story 6.2 implementou a taxa de câmbio como se o valor digitado fosse em KK (milhões). O usuário testou e percebeu que, pra representar o mesmo profit (ex.: 80kk), tinha que digitar `80` no formulário de Meta mas `8000000`/`80000000` no Conversor — os dois campos estavam em escalas diferentes. Causa raiz: taxas reais de TC no Tibia são em dezenas de milhares de **gold puro** (ex.: "Issobra a 45.000 por TC" do pedido original do usuário), nunca em milhões — 45.000 KK seria 45 bilhões de gold por TC, o que não existe no jogo. Confirmado com o usuário: a correção certa é gold puro em **todo** campo monetário, não KK em lugar nenhum.
[Fonte: conversa com o usuário, 2026-08-31 — não há documento de arquitetura pra citar aqui, é uma correção de requisito]

**Formulas atuais que mudam de nome (não de forma):**
```js
// ANTES (src/lib/currencyConverter.js) — errado, tratava kk como se fosse a unidade da taxa
export function kkToTc(kk, kkPerTc) { return kk / kkPerTc }
export function kkToBrl(kk, kkPerTc, brlPer250Tc) { return tcToBrl(kkToTc(kk, kkPerTc), brlPer250Tc) }

// DEPOIS — mesma forma, unidade correta (gold, que já é a unidade real de sessions.balance e goals.target_gold)
export function goldToTc(gold, goldPerTc) { return gold / goldPerTc }
export function goldToBrl(gold, goldPerTc, brlPer250Tc) { return tcToBrl(goldToTc(gold, goldPerTc), brlPer250Tc) }
```
`goalCalculator.js` (Story 6.3) **não muda** — já trabalha inteiramente em gold (`targetGold`, `profitSoFarGold`), nunca teve o bug de unidade. O bug estava só na camada de UI/taxa de câmbio (Story 6.2) e no formulário de Meta (Story 6.3, só na entrada — `kkToGold(Number(targetKk))` no submit, que esta story remove).
[Source: src/lib/currencyConverter.js; src/lib/goalCalculator.js; src/pages/Goals.jsx (GoalForm.submit, versão atual)]

**Técnica recomendada pro input formatado (evita reinventar posicionamento de cursor):**
Pra gold: guardar só os dígitos (`e.target.value.replace(/\D/g, '')`), formatar pra exibição com `toLocaleString('pt-BR')`. Pra reais: tratar os dígitos digitados como **centavos** (padrão "input de calculadora" — digitar `4750` sempre produz `R$ 47,50`, nunca exige o usuário digitar o separador decimal) — essa técnica evita quase todos os bugs comuns de input de moeda (cursor no meio do decimal, ponto vs vírgula, etc.). Aceitar que o cursor vai pro final do campo a cada tecla digitada — não é um problema real pra campos curtos como taxa de câmbio ou valor de meta, e evitar essa complexidade extra é a escolha certa pro tamanho deste projeto (sem lib de máscara de input nas dependências do `package.json`).

**Padrão de componente `ui/` a seguir:**
`src/components/ui/Input.jsx` exporta múltiplos componentes relacionados do mesmo arquivo (`Input`, `Textarea`, `Select`, `Label`, todos reaproveitando `baseClass`) — `FormattedNumberInput.jsx` deve seguir a mesma convenção (2 exports do mesmo arquivo, mesma classe base visual).

**Finding (não bloqueante, severidade baixa):** `FormattedCurrencyInput` (`src/components/ui/FormattedNumberInput.jsx:23-44`) usa a técnica "dígitos como centavos", que funciona perfeitamente pra digitação normal (o caso de uso do AC 2) e até pra colar um valor com 2 casas decimais. Mas colar um valor com **1 casa decimal** (ex.: `47,5` em vez de `47,50`) produz um resultado errado — os dígitos `475` viram R$ 4,75 em vez de R$ 47,50, porque a técnica sempre trata os 2 últimos dígitos como centavos, não interpreta separador decimal de verdade. Caso de uso raro (colar em vez de digitar, com precisão não-padrão) — não afeta o fluxo principal, mas vale documentar como débito técnico caso vire um problema real de uso.

**Limitação desta revisão (herdada do Dev):** sem credenciais de login do usuário, não testei o fluxo autenticado ao vivo. Toda a verificação foi por code review + scripts isolados + lint/build. Migration confirmada aplicada pelo usuário (via mensagem no chat).
